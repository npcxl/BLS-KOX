## Rust 后端 AI 对话 500 错误修复

### 问题
`POST /api/ai/chat/completions` 返回 500，message 为 `AI 服务返回错误 (401): ... api key: ****e60c is invalid`。

### 根因
Rust 后端 `stream_completions` 只用 `.env` 的 `OPENAI_API_KEY`（无效的占位 key `sk-882c21...e60c`），**完全没有读数据库 `ai_model_config` 表**。而 Koa 后端（bls-ai-service 的 `factory.ts`）是**优先从数据库读 key** 的（`getModelConfigs()` → `/api/system/ai-model/internal-list`）。

数据库 `ai_model_config` 表实际存有真实有效 key：
- `ai_cfg_002`（DeepSeek V4，`deepseek-chat`）：`api_key = "sk-ad7e5...f6ea"`（35位真实 key）
- `ai_cfg_001`（Qwen2.5 本地 ollama，默认项 is_default='1'）：`api_key=null`，`base_url=http://host.docker.internal:11434`

用户说"key 是加密过的"是误解——数据库存的是明文 key，前端列表只做了掩码显示（`sk-8****60c`）。

### 修复
在 `bls-rust-server/src/api/ai/chat.rs` 新增 `load_ai_config()` 函数：
- 按请求的 `model`（modelId）从 `ai_model_config` 表查 provider/model_id/api_key/base_url/temperature/timeout_ms
- key 为空或 `CHANGE_TO_` 前缀时降级到 `.env`
- 需 `use sqlx::Row;` 导入才能用 `row.get()`

## 后续：504 Gateway Timeout（SSE 流式超时）排查与修复

### 现象
key 修复后，`/api/ai/chat/completions` 从 500 变成 504。前端报 `[错误] 请求失败(504)`。

### 排查过程（三个独立 bug）
1. **DECIMAL 解码 panic**：`load_ai_config` 里 `row.get()` 读 `temperature`（DECIMAL(3,2)）时，SQLx 0.8 MySQL 驱动**既不能用 String 也不能用 f32 解码**，导致 ColumnDecode panic → tokio worker 崩溃 → 请求挂起 → 504。
   - 修复：SQL 里用 `CAST(temperature AS DOUBLE)`、`CAST(timeout_ms AS SIGNED)` 转类型，Rust 端用 `f64`/`i64` 读。

2. **验证 Rust 端 SSE 本身正常**：直接 curl 6002（用 superadmin/123456 登录拿 token）→ 200 + `text/event-stream` + 13 chunks 流式，1.17 秒完成。**Rust 后端 SSE 完全正常**。

3. **根因：响应头延迟发送**。Koa 后端（bls-ai-service `chat/index.ts`）用 `ctx.respond=false; ctx.res.writeHead(200, text/event-stream)` **立即写响应头**，再流式写内容。而 Rust 的 `stream_completions` 是 async fn，**先 await 上游 DeepSeek 响应头（首次 3.5 秒）才返回 Sse**，axum 才写响应头。这 3.5 秒空窗让 umi dev server（http-proxy-middleware）收不到任何字节 → 判定超时 → 504。
   - 修复：把 `stream_completions` 改成**同步返回 `Sse`**（非 async），用 `futures_util::stream::unfold` 构造惰性流，首个 poll 才发上游请求。响应头立即发出。

### 关键结论
- Rust 后端 AI 链路完整可用（从 DB 读 key → 调 DeepSeek → SSE 流式返回）
- 504 根因是"响应头延迟发送"，已通过惰性流重构修复
- 测试账号：superadmin / 123456（MD5 `e10adc3949ba59abbe56e057f20f883e`）
- 登录接口可用 `X-Internal-Secret` 头绕过 replay 中间件

### 待验证
- 重构后需用户重启服务验证前端是否正常流式输出

## 401 根因：Rust JWT 字段名与 Koa 不一致（snake_case vs camelCase）

### 现象
分流到 7201 后，前端 AI 接口返回 401。

### 根因
- Koa bls-server 签发的 JWT 字段是 **camelCase**：`userId`、`tenantId`、`tokenType`（`bls-server/src/shared/types/current-user.ts` 的 `JwtPayload`）
- Rust 后端签发的 JWT 字段是 **snake_case**：`user_id`、`tenant_id`、`token_type`（`auth/jwt.rs` 的 `Claims`）
- bls-ai-service (7201) 的 `middleware/auth.ts` 读 `payload.userId/tenantId/tokenType`，Rust 的 snake_case token 解析出 undefined，`tokenType !== 'access'` 失败 → 401

### 修复
在 `bls-rust-server/src/auth/jwt.rs` 的 `Claims` 加 serde rename：`user_id`→`userId`、`tenant_id`→`tenantId`、`token_type`→`tokenType`。其余字段（sub/username/perms/jti/exp/iat）本身一致。

### 注意
- 改字段名后旧 token（snake_case）失效，需重新登录
- Rust 内部 `.user_id` 字段名访问不受影响（serde rename 只改 JSON）

## 最终根因：umi 4 dev server 压缩中间件缓冲 SSE 导致 504

### 现象
JWT 修复后，直接打 7201 完全正常（models 返回 code:0 + 数据，completions 返回 text/event-stream 完整流），但前端走 umi proxy (9000) 仍报 `请求失败(504)` 和 `请求失败()`（空状态码）。

### 根因
umi 4 dev server 默认自带 compress 压缩中间件（GitHub issue #11453），会缓冲 SSE 流式响应，导致无法实时透传 → 504。这与后端无关（Rust 直连正常、7201 直连也正常，走 umi proxy 都 504）。

### 修复
`bls-admin/package.json` 的 dev 脚本加环境变量 `UMI_DEV_SERVER_COMPRESS=none` 关闭压缩：
```
"dev": "cross-env UMI_ENV=dev MOCK=none PORT=9000 UMI_DEV_SERVER_COMPRESS=none max dev"
```
官方 4.1.5 声称修复，但 @umijs/max 4.6.57 仍需显式设置。

## 最终根因：7201 的 BLS_SERVER_URL 指向 7001（无服务）→ fetch failed → 降级无效 key → 401

### 现象
前端 AI 对话返回 `[错误] AI 服务返回错误 (401)`，同时 7201 日志报 `[UsageTracker] report error: fetch failed`。

### 根因链
1. 7201 的 `.env` 里 `BLS_SERVER_URL=http://localhost:7001`（错！7001 是 docker 里的 Koa，本机没跑）
2. 7201 读模型配置时调 `localhost:7001/api/system/ai-model/internal-list` → 连不上 → `fetch failed`
3. 读配置失败 → 降级到 `.env` 的无效 key `OPENAI_API_KEY=sk-882c21...`
4. 用无效 key 调 DeepSeek → 401
5. 前端显示 `[错误] AI 服务返回错误 (401)`

### 修复
`bls-ai-service/.env` 的 `BLS_SERVER_URL` 从 `http://localhost:7001` 改为 `http://localhost:6001`（本机 Koa 主后端）。

### 关键事实
- 数据库 `ai_model_config` 表里 DeepSeek 的 key 已被用户改为 `sk-afbdc43e15b143ea81c6f02df431dad2`（有效，直接调 DeepSeek 返回 200）
- 7201 的 `OPENAI_API_KEY=sk-882c21...` 是无效的（fallback 用）
- 7201 读模型配置走 `BLS_SERVER_URL`，不上报走同一个 URL（`/api/system/ai-usage/report`）
- 本机端口：6001 Koa、6002 Rust、7201 AI 微服务都在跑，7001 没跑
