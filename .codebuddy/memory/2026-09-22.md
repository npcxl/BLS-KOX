### 一、Tianai 轨迹契约（唯一契约 = 官方 ImageCaptchaTrack）

- 从 `~/.m2` 的 `tianai-captcha-1.5.3-sources.jar` 里核对了官方源码，确认：
  - `ImageCaptchaTrack` 字段：`bgImageWidth/bgImageHeight/templateImageWidth/templateImageHeight/
    startTime/stopTime/trackList[{x,y,t,type}]`，`type ∈ {DOWN,MOVE,UP,CLICK}`（`TrackTypeConstant`）。
  - 默认校验器是 `SimpleImageCaptchaValidator`（**不是** `BasicCaptchaTrackValidator`），
    滑块只看 `(last.x - first.x)/bgImageWidth ≈ randomX/bgImageWidth`；点选只看 `type=CLICK` 的点。
  - 官方 `matching()` 内部用 `getAndRemoveCache` → 上游 challenge id **一次性**。
  - `ImageCaptchaVO.data` 是 `CustomData.getViewData()`（不含答案），SLIDER 的模板图是整条背景等高。
  - `checkClickCount` 默认 4，且 **viewData 里没有点击数量**（前端拿不到）。
- 前端 `TianaiCaptcha/index.tsx` 重写：只信上游尺寸，指针/触摸/键盘三条输入路径产出同一 DTO；
  尺寸缺失即显示"加载失败+刷新"，不再用 320×160 / 50×50 兜底，也没有 randomY。
- 新增契约测试 `components/TianaiCaptcha/__tests__/tianai-track.test.tsx`。
  ⚠ jsdom 下该测试必须 `vi.mock('@umijs/max', () => ({ request: vi.fn() }))`，
  否则 `@/services/auth/captcha` 会拉起 umi 的打包产物，报
  `Invariant violation: "new TextEncoder().encode("") instanceof Uint8Array"`。

### 三、安全降级修复（核心漏洞）

- 拆成两个判断：`isTianaiRequested`（只看 `captcha_tianai_enabled`：**决定风控是否升级**）
  与 `isTianaiConfigured`（+ 是否有 `TIANAI_BASE_URL`：决定能不能跑）。
- 旧实现把"没配地址"当成"不需要第二层" → 高风险账号被**静默降级**成只做 ALTCHA 并照常拿 ticket。
  现在：要求升级但服务不可用 → `throw await secondaryUnavailable()`（50302 fail closed）。
- 健康检查改为**只接受 2xx + 可解析的 JSON 对象**（旧版 `<500` 都算健康）。
- 第二层技术故障 → 响应里**补发新的 escalationGrant**，前端自动换 challenge，不要求用户先失败一次。
- 第二层会话在**调用上游之前** GETDEL（上游自己也是 getAndRemoveCache，请求一发出 id 就作废）。

### 四、ticket / escalation grant

- Redis key 与 used-marker 改为 `sha256(ticket)`（`captcha:ticket:{hash}` / `captcha:ticket-used:{hash}`），
  明文 ticket 永不出现在 key / 日志 / 审计。
- `CaptchaTicketService` 的 Redis 故障统一成 `CaptchaUnavailableError`（50301），与 `CaptchaStore` 一致，
  否则前端 `CAPTCHA_ERROR_CODES` 不认 50302 会当成密码错误。
- 新增 `captcha:escalation:{sha256(grant)}`：只有风控升级才签发，`/generate?provider=TIANAI`
  必须先 GETDEL 消费它，否则 40011（防止公开接口刷昂贵的图片资源）。
- 限流规则从已不存在的 `/api/auth/captcha/*` 改回真实端点 `/api/captcha/{config,generate,verify}`。

### 五、审计事件拆分（用户现场提问发现）

用户看到同一秒出现 `CAPTCHA_POW_PASSED`(LOW) + `CAPTCHA_SECONDARY_REQUIRED`(MEDIUM)。
根因：`service.ts` 里"风控命中但未启用第二层，只记原因"这条分支**复用了** `CAPTCHA_SECONDARY_REQUIRED`，
而它本意是"真的要求第二层、本次不发票证"。同一次 `/verify` 就会写出两条语义矛盾的记录。
修复：新增 `CAPTCHA_RISK_NOTED`（LOW，仅记录），两者互斥（有对应测试 `7d`）。
