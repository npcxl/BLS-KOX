## ALTCHA 报「Secure context (HTTPS) required.」（用户贴了浏览器报错）

根因：**ALTCHA v3 的 PoW 走 WebCrypto（`crypto.subtle`），浏览器只在安全上下文提供它**。
`node_modules/altcha/dist/.../altcha.js` 里写死了 `const {isSecureContext} = globalThis; if
(!isSecureContext) throw new Error("Secure context (HTTPS) required.")`，**没有任何开关可绕过**。
`isSecureContext` 为 true 的只有 `https://…` / `http://localhost` / `http://127.0.0.1`，
`http://<局域网IP>:8000` 不满足 → 第一层永远解不出来 → 服务端要求 token → 登录被卡死。

处理（前端显式失败，不再无限等待）：

- `captcha-machine.ts`：state 增加 `envBlocked`，新增事件 `ENV_UNSUPPORTED`（清空凭证 + phase=error
  + hint），`canSubmit()` 首位判断 `envBlocked` → false，`phaseAfterUsernameChange` 也保持 error。
- `hooks/useLoginCaptcha.ts`：配置已加载且**验证码开启**时若 `window.isSecureContext === false`
  → dispatch `ENV_UNSUPPORTED`；导出 `isInsecureContext()` 与 `INSECURE_CONTEXT_HINT`。
  验证码关闭时**不拦**（原登录流程不需要 WebCrypto）。
- `components/AltchaCaptcha`：新增 `onError`，挂载时检测非安全上下文立即上报，并转发 widget 的
  `statechange → error`；登录页接 `onError={captcha.onAltchaError}`（区分"环境无解"与"组件加载失败"）。
- 测试：机器 +2（envBlocked 后禁止提交、改用户名也不能绕过）、hook +2（非安全上下文报错；
  验证码关闭时不受影响）→ 前端 9 文件 / 82 用例全绿。

开发环境绕过方式（已写进 docs）：用 `localhost` 访问 / 给 dev server 配 HTTPS /
`chrome://flags/#unsafely-treat-insecure-origin-as-secure`（仅调试）。**生产必须 HTTPS。**

## 用户报「输入完密码就 50301 CAPTCHA_SERVICE_UNAVAILABLE」的定位

50301（`CaptchaUnavailableError`）**只有两个来源**，先看是哪个请求：

1. `POST /api/auth/captcha/secondary/challenge`（或 `/secondary/verify`）→ **策略要求第二层但
   Tianai 不可用**：`TIANAI_BASE_URL` 为空 / 服务不可达 / 超时 / 上游报错，或
   `secondaryProvider` 被设成非 tianai。触发时机正是「用户名稳定 → 带 username 重拉策略」，
   所以表现为"输完用户名/密码就报错"。**这是最可能的原因**（用户环境没有 Tianai）。
   触发条件：`mode=always`、同账号连续失败 ≥ `forceAfterFailures`、IP 多账号、IP 高风险、
   超管账号、UA 异常。
2. `POST /api/auth/login` → **Redis 不可用**（`captcha:token:*` 消费失败即 fail closed）。

改进（可运维性，对外文案不变，仍是统一的 50301）：

- `service.ts`：第二层 provider 不可用的两个分支补 `logger.warn`，日志里带 `hint`
  （"设置 TIANAI_BASE_URL …或把 mode 设为 off"）。
- `app.ts`：启动时若 `TIANAI_BASE_URL` 为空 → 打印显著告警，避免"配了验证码却没人能登录"查半天。
- `docs/login-captcha.md` 新增 §2.1「排障：50301」对照表 + 复现/确认命令（config 接口、
  日志关键字、`redis-cli --scan --pattern 'captcha:fail:*'`）+ 三种恢复方式。

经验：**fail closed 的设计要配"可运维的信号"**——统一错误码给客户端是对的，但服务端必须留下

   处理两处：
   - `src/app.ts`：`app.on('error')` 按 status 分级 —— 4xx 业务拒绝打 `logger.warn('Request rejected')`，
     只有 5xx/未知异常才 `logger.error('Unhandled application error')`。避免验证码/鉴权类预期错误刷 ERROR。
   - `src/pages/user/login/index.tsx`：新增 `pendingLoginRef` + `doLoginRef` —— 登录被 40010~40013 拒绝后

     （`doLogin` 定义在该回调之后，必须用 ref 转发，否则依赖数组求值触发 TDZ。）

结论/经验：

- **动态配置改枚举后，一定要给存量数据写 UPDATE**，否则线上会一直刷 "invalid enum" 告警。
- **4xx 业务错误不要打成 ERROR**，否则告警噪音淹没真实故障。
- 验证码被拒后的 UX 关键：不是让用户重填表单，而是**挂起并自动续跑**。

## 前端 bug：登录页一直停在「正在后台完成安全校验…」（用户反馈）

## 性能：captcha 三个接口都 ~2.5s（用户反馈"这个时间是不是有点长了"）

根因不在 PoW，在 `bls-server/src/shared/utils/ip.ts` 的 `resolveClientIp()`：

- `buildRequestMeta()` 每个请求都调它；本地 `ctx.ip` 为 `::1`/`127.0.0.1` → `normalizeIp()` 判空
  → 去请求 `https://api.ipify.org` 和 `https://ipapi.co` 两个**无超时**的 HTTPS 接口。
- 国内基本连不通，每个各挂 ~1.2s ≈ 2.4s；失败返回 null **又不写缓存**，于是每个请求都重来一遍
  → config / challenge / verify 全部 ~2.5s（登录接口同样中招）。
- 附带 bug：旧逻辑即使已拿到真实客户端 IP，也会用「服务端出口 IP」覆盖返回值 → 登录 IP 记错。

修复：

- 已拿到真实客户端 IP → **直接返回**，不再请求公网接口。
- 只有拿不到（本地回环直连）才回退公网出口 IP，且 `AbortSignal.timeout(1000)`；
  结果写 Redis 缓存，**失败也负缓存 60s**（哨兵 `'0'`），避免被墙时每请求重试。
- 新增 `PUBLIC_IP` 环境变量显式指定（无外网 / 内网部署强烈建议），已写进 `.env.example`。

经验：**任何出站 fetch 都必须带超时**；**失败结果也要缓存（负缓存）**，否则"失败"路径比"成功"路径更慢，
且在受限网络下会周期性放大成每个请求几秒。

经验：**凡是参与渲染的状态一律用 useState；ref 只用于「不渲染」的一次性值（token、重试标记）。
把 ref 当渲染源是静默 bug —— tsc 和 lint 都查不出来，只有肉眼能看见。**

排查命令备忘：改完大范围重构后，用 `search_content` 全局搜已删除的符号名
（`CAPTCHA_SECRET` / `secondaryTypes` / `behavior-collector` / `CaptchaChallenge` / `captcha/image`），
能快速揪出散落在 bls-memory 各页里的过时描述——**代码编译通过 ≠ 文档一致**。

## 【重要】登录人机验证「数据无效」根因（用户实测报障，已修）

现象：config → generate → widget 求解都成功，但 `/api/captcha/verify` 恒返回
`{status:'failed', reason:'PAYLOAD_MALFORMED'}`，前端显示「人机验证数据无效，请重试」。

根因：`bls-server/src/security/captcha/service.ts` ALTCHA 分支里，
验签**通过之后**取 challenge nonce 用于一次性消费的代码写成了

```ts
const nonce = challengeNonceOf((meta.payload as any)?.challenge ?? {});
```

而 `meta.payload` 是**前端提交的 base64 字符串**（不是解码后的对象），
`payload.challenge` 永远 `undefined` → nonce 为空 → 直接判 `PAYLOAD_MALFORMED`。
即：PoW 明明通过了，却因为读错字段被当成"数据无效"。

修复（3 处）：

1. `providers/types.ts`：provider 级 `CaptchaVerifyResult` 增加 `challengeNonce?: string`；
2. `providers/altcha-provider.ts`：验签通过时返回
   `challengeNonce: challengeNonceOf(payload.challenge)`（**从解码后的 challenge 取**）；
   同时把 `VERIFY_ERROR`（官方库抛异常=我方环境问题）从 `failed/PAYLOAD_MALFORMED`
   改判为 `technical_error/INTERNAL_ERROR` —— 服务端故障不能计入用户验证失败；
3. `service.ts`：改用 `outcome.challengeNonce`，并加注释警告不要读 `meta.payload.challenge`。

验证（用官方 `altcha/lib` 在 Node 里真跑 PoW，探针脚本临时写过又删掉）：
`generate → solveChallenge → verify` = `status:'passed'` + `captchaTicket`；
**同 payload 再提交一次 → `CHALLENGE_EXPIRED`**（说明 challenge 一次性消费也恢复了）。

经验：**协议里"字符串里套 JSON"的字段，任何一层都可能误当成对象读**。
base64 payload 这种设计，取值必须走统一的 decode 函数，并在 provider 边界就把需要的东西
（nonce / signedData）解析出来返回给上层，不要留给上层猜。

## 用户复报 PAYLOAD_MALFORMED：其实是「旧页面」+ 前端请求风暴

抓到的结果（当前代码 **完全正常**）：

顺带修掉真 bug：`useLoginCaptcha` 里有一条**没有 debounce 的兜底 effect**——

```ts
// 反例：username 每变一次都会清空 altchaChallenge → 每个字符触发一次 generate
useEffect(() => {
  if (state.phase !== 'solvingSilent' || !state.config?.enabled) return;
  if (altchaChallenge) return;              // ← 失败时永远为 null，还会自激成请求风暴
  void fetchSilentChallenge(state.username, state.config);
}, [state.phase, state.username, altchaChallenge, ...]);
```

改为：只在 `TICKET_EXPIRED` 定时器里**显式**重取；`onAltchaError` 自动重试上限 2 次；
`USERNAME_DEBOUNCE_MS` 400 → 500。

经验：**"清空状态" + "状态为空就请求" 两条 effect 组合起来就是请求风暴**——
凡是 effect 依赖某个会被主动清空的字段，一定要配 in-flight / 次数守卫。

## 用户报 `GET /api/captcha/config` **504 Gateway Timeout** —— 是 dev proxy 的假象

关键判据：**Koa 自己不产生 504**（全仓搜 `504` 只有 PNG 魔数 `89504e47`）。
直连 Koa 立刻 200：

```
Invoke-WebRequest http://127.0.0.1:6001/api/captcha/config?username=superadmin
→ 200（冷启动 2794ms / 热 279ms）
```

真实原因：**umi dev proxy（9000 → 6001）把上游 ECONNREFUSED 映射成了 504**。
请求正好撞上 `tsx watch` 重启 —— 我每改一个 `bls-server` 下的文件它都会重启，
窗口内的请求必然失败（前面已经出现过一次 `ECONNREFUSED 127.0.0.1:6001`）。

**排障口诀：看到前端 4xx/5xx，先绕过代理直连后端端口复测一遍**，别急着改业务代码。

顺带修掉两处真实浪费（代理超时只是放大器）：

1. `api/captcha/index.ts` 的 `GET /config` 原本走 `buildRequestMeta()` —— 为了一个
   **只判断租户**的接口去做客户端 IP 解析（本机回环时还会去访问公网出口 IP 接口，
   每个 1s 超时 + Redis 读写）。改成只用两个纯函数 `resolveTenantDomain(ctx)` +
   `extractRequestIp(ctx)` → 冷启动 2794ms → **493ms**。
   经验：**路由按需取 meta**，不要所有接口都套用"全量请求元信息"。
2. `useLoginCaptcha` 的 debounce 里原本**每次输入都重新拉 `/config`** ——
   那是旧"下发 requiredStage"设计的遗留：统一 ticket 架构下公开配置只有
   `enabled / primaryProvider / fallbackProvider / tianaiEnabled`，**不含任何按用户名变化的策略**。
   去掉后登录页 capcaha 请求从 `config×2 + generate×N` 变成 **`config×1 + generate×1`**。

另给 `bls-admin/config/proxy.ts` 的 `/api/` 补了显式 `proxyTimeout: 60000`
（**改 proxy 必须重启 dev server 才生效**），让超时行为可预期。

复验（用真浏览器，用户名跟用户报的一样 `superadmin`）：
`config(1次) → generate(1次) → verify passed + captchaTicket`。

**仍未做**：`/config` 热请求还有 ~220ms，根因是 `findTenantByDomain` 无缓存、
每次两条远程 MySQL 查询（DB 在 117.72.118.165）。想优化要权衡：加短 TTL 缓存会让
「租户刚被停用」在 TTL 内仍可登录，涉及安全语义，未擅自改。
