## 运行日志排障：人机验证（用户贴了真实运行日志）

现象（服务端日志）：

1. `[WARN] [dynamic-config] invalid enum, using default {key: sys.login.captcha.provider, val: 'builtin'}`
   —— **已部署库里还是旧种子写的 `builtin`**（ALTCHA 化后枚举只剩 `altcha`/`tianai`）。
   代码会回退默认值所以功能正常，但每次解析都告警。
   处理：在 `migrations/20260922_017_login_captcha.sql` 末尾追加可重复执行的存量修正
   （`UPDATE ... SET config_value='altcha' WHERE config_key=... AND config_value NOT IN ('altcha','tianai')`），
   并**软删除** 3 个废弃键（silentThreshold / secondaryTypes / maxAttempts，`deleted=1`）。
   ⚠ 该 migration 只在已部署库上跑；`sql/Init.sql` 本来就是 6 行新值，无需改。

2. `[ERROR] Unhandled application error { CaptchaRequiredError: 请先完成人机验证 }`
   —— 后端行为**正确**（开启后无 Token 一律拒绝，fail closed），问题在客户端没走验证流程
   （旧前端构建 / 旧标签页 / 配置拉取失败）。
   处理两处：
   - `src/app.ts`：`app.on('error')` 按 status 分级 —— 4xx 业务拒绝打 `logger.warn('Request rejected')`，
     只有 5xx/未知异常才 `logger.error('Unhandled application error')`。避免验证码/鉴权类预期错误刷 ERROR。
   - `src/pages/user/login/index.tsx`：新增 `pendingLoginRef` + `doLoginRef` —— 登录被 40010~40013 拒绝后
     挂起这次登录，widget 重新求解成功（拿到新 captchaToken）后**自动补发登录**，用户不用再点一次。
     （`doLogin` 定义在该回调之后，必须用 ref 转发，否则依赖数组求值触发 TDZ。）
   手动提交时清 `pendingLoginRef`，避免重复登录。

结论/经验：

- **动态配置改枚举后，一定要给存量数据写 UPDATE**，否则线上会一直刷 "invalid enum" 告警。
- **4xx 业务错误不要打成 ERROR**，否则告警噪音淹没真实故障。
- 验证码被拒后的 UX 关键：不是让用户重填表单，而是**挂起并自动续跑**。

## 前端 bug：登录页一直停在「正在后台完成安全校验…」（用户反馈）

现象：challenge/verify 都成功（返回 `passed:true` + captchaToken），但界面上的 spinner 文案不消失。

根因：`AltchaCaptcha` 的 `solved` 属性传的是 `!!captchaTokenRef.current` —— **ref 变化不触发 React 重渲染**，
所以 `solved` 永远是首次渲染时的 `false`，静默验证完成后 UI 不会更新。

修复：

- 登录页新增 `const [captchaSolved, setCaptchaSolved] = useState(false)`，
  在 `exchangePayload` 成功时置 true，失败 / 切可见 / 服务异常 / `handleAltchaReset` /
  captcha 登录错误（4001x）时置 false；JSX 改传 `solved={captchaSolved}`。
- `AltchaCaptcha`：`display === 'invisible' && solved` 时**不渲染**加载文案（widget 仍保持挂载，
  保证后续 refresh / 重求解可用）。

## 性能：captcha 三个接口都 ~2.5s（用户反馈"这个时间是不是有点长了"）

根因不在 PoW，在 `bls-server/src/shared/utils/ip.ts` 的 `resolveClientIp()`：

- `buildRequestMeta()` 每个请求都调它；本地 `ctx.ip` 为 `::1`/`127.0.0.1` → `normalizeIp()` 判空
  → 去请求 `https://api.ipify.org` 和 `https://ipapi.co` 两个**无超时**的 HTTPS 接口。
- 国内基本连不通，每个各挂 ~1.2s ≈ 2.4s；失败返回 null **又不写缓存**，于是每个请求都重来一遍
  → config / challenge / verify 全部 ~2.5s（登录接口同样中招）。
- 附带 bug：旧逻辑即使已拿到真实客户端 IP，也会用「服务端出口 IP」覆盖返回值 → 登录 IP 记错。

修复：

- 已拿到真实客户端 IP → **直接返回**，不再请求公网接口。
- 只有拿不到（本地回环直连）才回退公网出口 IP，且 `AbortSignal.timeout(1000)`；
  结果写 Redis 缓存，**失败也负缓存 60s**（哨兵 `'0'`），避免被墙时每请求重试。
- 新增 `PUBLIC_IP` 环境变量显式指定（无外网 / 内网部署强烈建议），已写进 `.env.example`。

经验：**任何出站 fetch 都必须带超时**；**失败结果也要缓存（负缓存）**，否则"失败"路径比"成功"路径更慢，
且在受限网络下会周期性放大成每个请求几秒。

经验：**凡是参与渲染的状态一律用 useState；ref 只用于「不渲染」的一次性值（token、重试标记）。
把 ref 当渲染源是静默 bug —— tsc 和 lint 都查不出来，只有肉眼能看见。**

排查命令备忘：改完大范围重构后，用 `search_content` 全局搜已删除的符号名
（`CAPTCHA_SECRET` / `secondaryTypes` / `behavior-collector` / `CaptchaChallenge` / `captcha/image`），
能快速揪出散落在 bls-memory 各页里的过时描述——**代码编译通过 ≠ 文档一致**。
